# v0.8.x Correlation, Merit, and Promotion Specification

## Purpose

This document defines the planned v0.8.x observation, correlation, behavioral merit, and promotion pipeline for `accessible-tpi-chain`.

It is a design/specification document only. It does not imply that the described modules or fields already exist in v0.7.6.

### Staged-development rule

- **Documented surface**: broader planned architecture.
- **Implemented surface**: what is already proven in code.
- **Gap**: intentional, not a bug.

The v0.8.x system introduces:

- a 90-day observer period
- passive network correlation analysis
- wallet/operator continuity signals
- behavioral merit accumulation
- promotion gating at observation end
- permanent historical flag retention

---

## Architectural split

### `correlation.rs`
Handles network timing analysis, passive RTT fingerprinting, cluster detection, correlation windows, and integrity confidence contributions from network behavior.

### `behavioral_merit.rs`
Handles wallet continuity, wallet age, transaction cadence, uptime continuity, and behavioral merit signals from on-chain and network-observable activity.

### `integrity.rs`
Handles final aggregation, promotion decisioning, group penalties, historical flag lifecycle, and escalation rules after promotion.

### Existing modules used as foundations

- `peer_manager.rs` — peer identity, connection state, liveness, timestamp history
- `types.rs` — chain state, blocks, transactions, mempool
- `metrics.rs` — observability only; not state ownership
- `network.rs` — message flow and timing event capture
- `rpc.rs` — exposure for operators and dashboards

---

## Ownership and storage rules

- `metrics.rs` is observability only.
- It surfaces state but does not own canonical per-peer or promotion data.
- Canonical per-peer data lives in `peer_manager.rs` on `PeerInfo` or in the new modules.
- Aggregate analysis objects live in the new modules.
- Chain state remains in-memory in `types.rs`.

---

## Scope rule

`correlation.rs`, `behavioral_merit.rs`, and `integrity.rs` are `valid-blockchain` branch only. They are not part of `private-network` or the `main` protocol base.

---

## Retention model

### BroadcastAnchor retention

`BroadcastAnchor` objects must be held in a bounded ring buffer, not an unbounded in-memory log.

Reason:
- the observation window spans 90 days
- you cannot keep every broadcast event forever in memory
- once associated `PeerResponseSample` objects have been consumed by the correlation pass, older anchors should be pruned

This matches the Zero Footprint principle: you do not keep what you no longer need.

---

## Observation lifecycle

### Observer clock start

The 90-day observer clock starts on first valid handshake completion.

The clock does not pause for:

- inactivity
- identity rotation
- temporary disconnects

Inactivity is a signal that contributes to decay and merit loss, not a pause condition.

---

## Identity rotation

Identity rotation does not erase context if the underlying behavioral fingerprint remains the same.

- a fresh identity restarts the observer clock
- the same infrastructure fingerprint can be re-detected
- historical flags remain attached to the contextual record
- repeated restart attempts are self-punishing under the 90-day model

---

## Data model

### 1. `BroadcastAnchor`

Phase: collection

Marks the exact moment a measurable network event occurred. This is the timing origin for all downstream samples. It is not a verdict object. It should be inserted into a bounded ring buffer.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct BroadcastAnchor {
    pub anchor_id: String,
    pub slot: u64,
    pub message_type: String,
    pub emitted_at: u64,
    pub emitter_peer_id: String,
    pub block_hash: Option<String>,
    pub broadcast_scope: String,
    pub reference_points: Vec<String>,
    pub notes: Option<String>,
}
```

### 2. `PeerResponseSample`

Phase: collection

Records a peer's measured response relative to an anchor. `delta_ms` is the main correlation measurement. `rtt_ms` is passive RTT derived from normal protocol traffic. `rtt_asymmetry_ms` helps distinguish residential from datacenter behavior. This should be append-only until consumed by analysis.

`hop_signature` is present as an optional placeholder. Analysis may ignore it initially. Full path fingerprinting is deferred to a later phase.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct PeerResponseSample {
    pub sample_id: String,
    pub anchor_id: String,
    pub peer_id: String,
    pub observed_at: u64,
    pub delta_ms: u64,
    pub response_type: String,
    pub message_kind: String,
    pub transport_addr: String,
    pub session_id: String,
    pub rtt_ms: Option<u64>,
    pub rtt_asymmetry_ms: Option<i64>,
    pub hop_signature: Option<String>,
    pub validity_flags: Vec<String>,
}
```

### 3. `OperationalIdentity`

Phase: analysis / linkage

Binds node behavior to wallet continuity. The wallet is the most stable anchor in the operational bundle. Peer identity can rotate. Network path can change. Wallet continuity remains meaningful across the observer period.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct OperationalIdentity {
    pub node_id: String,
    pub wallet_address: String,
    pub wallet_public_key: String,
    pub first_seen_at: u64,
    pub last_seen_at: u64,
    pub wallet_age_days: u64,
    pub last_signed_at: Option<u64>,
    pub signing_cadence_score: f64,
    pub transaction_activity_score: f64,
    pub operator_behavior_score: f64,
    pub identity_stability_score: f64,
}
```

### 4. `RttLocationProfile`

Phase: collection + analysis

Passive RTT and location-confidence profile. Passive RTT is preferred over active ping. `physics_floor_violation = true` is a hard disqualifier for the location claim. Location is a soft signal except when physics is violated. `rtt_asymmetry_ms` helps distinguish residential from datacenter paths. This is not authoritative geolocation — it is a confidence layer.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct RttLocationProfile {
    pub peer_id: String,
    pub reference_point_id: String,
    pub sample_count: u64,
    pub rtt_samples_ms: Vec<u64>,
    pub rtt_min_ms: u64,
    pub rtt_median_ms: u64,
    pub rtt_mean_ms: f64,
    pub rtt_stddev_ms: f64,
    pub rtt_jitter_score: f64,
    pub rtt_asymmetry_ms: f64,
    pub baseline_distance_score: f64,
    pub physics_floor_violation: bool,
    pub location_confidence_score: f64,
    pub infrastructure_similarity_score: f64,
    pub vpn_proxy_likelihood: f64,
    pub datacenter_likelihood: f64,
    pub residential_likelihood: f64,
}
```

### 5. `CorrelationWindow`

Phase: analysis

Aggregates evidence across the 90-day observer period using rolling subwindows. This is a rolling statistical container, not a point-in-time snapshot. It accumulates across the full observer period. Confidence can rise and decay over time.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct CorrelationWindow {
    pub window_id: String,
    pub subject_id: String,
    pub window_start: u64,
    pub window_end: u64,
    pub observer_period_start: u64,
    pub observer_period_end: u64,
    pub sample_count: u64,
    pub subwindow_span_secs: u64,
    pub subwindow_count: u64,
    pub broadcast_anchor_ids: Vec<String>,
    pub peer_sample_ids: Vec<String>,
    pub arrival_variance_ms: f64,
    pub arrival_stddev_ms: f64,
    pub heartbeat_sync_score: f64,
    pub reaction_correlation_score: f64,
    pub rtt_profile_score: f64,
    pub rtt_asymmetry_score: f64,
    pub location_confidence_score: f64,
    pub cluster_id: Option<String>,
    pub cluster_size: u64,
    pub confidence_trend: String,
    pub flag_events: Vec<String>,
    pub decay_rate_applied: f64,
    pub analysis_notes: Option<String>,
}
```

### 6. `FlagRecord`

Phase: history

Append-only historical event record. Historical flags never disappear. They remain part of the permanent behavioral record and influence escalation logic even after clean recovery.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct FlagRecord {
    pub flag_id: String,
    pub timestamp: u64,
    pub confidence_at_flag: f64,
    pub reason_codes: Vec<String>,
    pub cluster_id: Option<String>,
    pub resolved: bool,
    pub resolution_timestamp: Option<u64>,
    pub resolution_outcome: Option<String>,
}
```

### 7. `NodeIntegrityScore`

Phase: analysis + promotion decision

Composite verdict used for promotion and escalation. `current_confidence` is mutable and can recover with clean behavior. `historical_flags` is permanent. Promotion uses both current score and history. A historical flag causes stronger scrutiny even if current confidence is clean.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct NodeIntegrityScore {
    pub subject_id: String,
    pub current_confidence: f64,
    pub confidence_floor: f64,
    pub confidence_ceiling: f64,
    pub network_timing_component: f64,
    pub rtt_component: f64,
    pub location_component: f64,
    pub behavioral_component: f64,
    pub wallet_component: f64,
    pub cluster_component: f64,
    pub promotion_blocking_threshold: f64,
    pub promotion_ready_threshold: f64,
    pub last_updated_at: u64,
    pub resolution_state: String,
    pub recovery_eligibility: bool,
    pub historical_flags: Vec<FlagRecord>,
}
```

### 8. `FlagPattern`

Phase: analysis + escalation

Pattern analysis across the historical flag log. Runs as part of promotion decisioning and as a periodic background pass. A node that develops a suspicious flag pattern mid-observation period triggers elevated scrutiny immediately.

`flag_intervals_secs` and `interval_stddev_secs` detect automated attack timing. `repeated_cluster_count` identifies nodes that keep appearing in the same cluster across identity rotations. `flags_post_recovery` distinguishes repeat offenders from single-event cases. `cross_node_matches` identifies nodes whose flag timing correlates with this node's across independent identity instances — the primary cross-node attacker pattern detection mechanism.

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct FlagPattern {
    pub subject_id: String,
    pub total_flag_count: u64,
    pub flag_timestamps: Vec<u64>,
    pub flag_intervals_secs: Vec<u64>,
    pub mean_interval_secs: f64,
    pub interval_stddev_secs: f64,
    pub cluster_ids_seen: Vec<String>,
    pub repeated_cluster_count: u64,
    pub peak_confidence_reached: f64,
    pub flags_post_recovery: u64,
    pub pattern_class: String,
    pub cross_node_matches: Vec<String>,
    pub last_analyzed_at: u64,
}
```

## Cluster model

Correlation analysis identifies clusters of nodes with similar timing signatures.

Cluster fields on `CorrelationWindow`:
- `cluster_id`
- `cluster_size`
- `cluster_confidence`
- `cluster_penalty_applied`

Cluster penalty requires both a minimum confidence threshold and a minimum cluster size threshold. Both are config-driven.

---

## Testnet vs mainnet

### Testnet
- Observer Bot is manual scaffolding
- merit is awarded manually
- leaderboard at end of testnet seeds the bootstrap validator set
- no automated merit pipeline required

### Mainnet
- no Discord dependency
- no manual awards
- behavioral merit derives from block production history, wallet continuity, chain-observable activity, and passive network telemetry

## Summary

This design separates collection, analysis, promotion decision, and historical record. That separation is the core v0.8.x boundary. The system is testnet-friendly, tunable, and staged. All three new modules belong to the `valid-blockchain` branch only.
